Descripción del proceso (ETL con SSIS)

El tratamiento de calidad de GBIF se implementó como un proceso ETL en SQL Server Integration Services (SSIS). El conjunto de datos crudos (2.129.220 registros y 50 variables) se cargó primero a una zona de staging para conservar el dato original y permitir reproducir el proceso; luego, mediante un Data Flow, se aplicaron las reglas de limpieza y se separaron los registros válidos de los que requieren revisión.

Objetivo
Corregir y controlar los problemas de calidad identificados en la Etapa 02 (coordenadas sin georreferenciar o fuera de rango, valores nulos, formatos y duplicados), conservando la trazabilidad del dato original y separando los registros dudosos.

Diseño del paquete (Control Flow y Data Flow)

El primer intento usó un Origen de archivo plano (Flat File) que leyó el archivo como texto y lo cargo en la DB luego se implemento en el data flow

Intento inicial con Origen de archivo plano (Flat File)

La carga a la zona de staging se completó correctamente. El tratamiento se implementó en el Data Flow con la cadena Origen de OLE DB → Conversión de datos → Columna derivada → División condicional y dos destinos.

Data Flow final: origen OLE DB, conversión de tipos, columna derivada y división condicional hacia limpio y revisión.

Columna derivada: se calculan motivo, campo_afectado, valor_original e iteracion_rev.

División condicional: la condición motivo == "" dirige a "Validos"; el resto cae en la salida predeterminada "Revision".

Eliminación de duplicados

La transformación Sort de SSIS se descartó porque, al ser un componente de bloqueo, reservó toda la tabla en memoria. La deduplicación se realizó en SQL con ROW_NUMBER(), mucho más eficiente para 2,1 millones de filas.

Deduplicación por occurrenceID: 568 duplicados eliminados (2.124.126 → 2.123.558).

Intento con el componente Sort (hallazgo)

Al usar el componente Ordenar (Sort) para eliminar duplicados, SSIS intentó cargar la tabla completa en memoria y agotó los recursos del equipo (“insufficient disk space”, con ~8,3 GB reservados por el componente). Este hallazgo justificó cambiar a la deduplicación en SQL.

Sort en el Data Flow

El componente "Ordenar" entra al flujo y falla la ejecución.

Error por memoria

“Insufficient disk space”: el Sort reservó ~8,3 GB.

Idempotencia y re-ejecución

Antes de cada ejecución se limpian las tablas destino (TRUNCATE de limpio.GBIF y revision.GBIF_Revision), de modo que volver a correr el mismo lote (id_lote) no genera registros duplicados. La deduplicación por occurrenceID refuerza la unicidad del resultado.

Iteraciones 2 y 3 (plan documentado)

Justificación de alcance
Cada iteración implica recomputar todo el pipeline (extracción desde el staging, conversión, derivación, división y deduplicación) sobre 2,1 millones de filas. El consumo de memoria y el tiempo de ejecución superan los recursos del equipo de trabajo (el intento con Sort llegó a reservar ~8,3 GB y agotó el disco temporal). Por limitaciones de hardware, las Iteraciones 2 y 3 se presentan como plan diseñado sin ejecutar.
